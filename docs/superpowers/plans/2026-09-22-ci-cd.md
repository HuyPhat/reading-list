# CI for Reading List Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GitHub Actions CI workflow to the Reading List repo that runs type-check, lint, a Prisma migration/seed validation, and a production build on every push to `main` and every pull request — then make it a required, blocking status check on `main`.

**Architecture:** A single-job GitHub Actions workflow (`.github/workflows/ci.yml`) installs dependencies with pnpm, applies the repo's committed Prisma migrations to a fresh SQLite database, seeds it, then runs `tsc --noEmit`, `eslint`, and `next build` in sequence. No deployment step — this is CI only. The workflow is verified by actually opening it as its own pull request and watching it run on GitHub (there's no way to verify a GitHub Actions workflow purely locally), and only after it's confirmed green does branch protection get enabled requiring it.

**Tech Stack:** GitHub Actions, pnpm 12.4.2, Node.js 24.x, Prisma 7.10.0 + SQLite (existing project stack, unchanged).

**Spec:** [docs/superpowers/specs/2026-09-22-ci-cd-design.md](../specs/2026-09-22-ci-cd-design.md) — read this alongside the plan; it has the full rationale for the CI-only scope decision and why migration validation is included.

## Global Constraints

- Package manager is pnpm `12.4.2`; Node version is `24.x` — these match what's actually installed and used in local development for this repo, and must be pinned exactly in the workflow (not left to float on `latest`).
- No automated test suite exists in this project (a deliberate decision documented in the project's own design spec) — CI does not run a test runner; its checks are type-check, lint, migration/seed validation, and build only.
- `DATABASE_URL` is a local SQLite file path (`file:./prisma/dev.db`), not sensitive data — set it directly as a workflow-level `env` value, not a GitHub Actions secret.
- This repo's established workflow (used for every change so far) is: commit on a feature branch, push, open a PR via `gh pr create`, verify, then merge — apply that same pattern here rather than pushing directly to `main`.
- Branch protection requiring the CI check is an explicit, already-approved decision (confirmed during brainstorming) — attempt it via `gh api`. If any step is blocked by a safety mechanism (this has happened before in this repo's history for direct-to-`main` operations), stop and report exactly what was attempted and why, rather than working around it.
- Do not enable required-status-check branch protection until the workflow has been observed to actually pass at least once on GitHub — an unproven required check would leave every future PR (including the one this plan itself produces) unable to merge.

### Task 1: CI workflow file and README badge

**Files:**
- Create: `.github/workflows/ci.yml`
- Modify: `README.md`

**Interfaces:**
- Produces: a GitHub Actions workflow named `CI` with a single job named `ci`, triggered on `pull_request` (base `main`) and `push` (to `main`) — Task 3 references this exact job name (`ci`) when configuring branch protection.

- [ ] **Step 1: Write `.github/workflows/ci.yml`**

```yaml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

env:
  DATABASE_URL: file:./prisma/dev.db

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 12.4.2

      - name: Set up Node
        uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: 'pnpm'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Apply database migrations
        run: pnpm exec prisma migrate deploy

      - name: Seed database
        run: pnpm exec prisma db seed

      - name: Type-check
        run: pnpm exec tsc --noEmit

      - name: Lint
        run: pnpm lint

      - name: Build
        run: pnpm build
```

Note the step order: `pnpm/action-setup` must run before `actions/setup-node`, because `setup-node`'s `cache: 'pnpm'` option needs `pnpm` already on `PATH` to locate the pnpm store for caching.

- [ ] **Step 2: Add a CI badge to `README.md`**

At the very top of `README.md`, before the first existing line, add:

```markdown

```

(Leave a blank line after the badge before the existing first line of the file.)

- [ ] **Step 3: Verify the YAML is well-formed**

Expected: `valid YAML` printed, no exception. (This only checks syntax, not whether the workflow actually runs — that's Task 2.)

- [ ] **Step 4: Commit on a new branch**

### Task 3: Require the CI check on `main`

**Files:** none (repo settings change via the GitHub API)

**Interfaces:**
- Consumes: the confirmed-green `ci` job name from Task 2, and the PR number from Task 2 (to confirm it can still merge once its check is green).

- [ ] **Step 1: Enable required status checks on `main`**

```bash
gh api --method PUT repos/HuyPhat/reading-list/branches/main/protection \
  -H "Accept: application/vnd.github+json" \
  --input - <<'EOF'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["ci"]
  },
  "enforce_admins": false,
  "required_pull_request_reviews": null,
  "restrictions": null
}
EOF
```

Using a raw JSON body via `--input -` here rather than `gh api`'s `-f`/`-F` field flags, since this endpoint requires explicit `null` for several fields and JSON is unambiguous about that in a way flag-based field construction isn't guaranteed to be across `gh` CLI versions.

If this call is blocked by a permission/safety mechanism, stop here and report exactly what was attempted (the command above) and why it's needed, rather than trying an alternate method to force it through.

- [ ] **Step 2: Verify the protection actually took effect**

```bash
gh api repos/HuyPhat/reading-list/branches/main/protection --jq '.required_status_checks.contexts'
```

Expected: `["ci"]` (or an array containing `"ci"`).

- [ ] **Step 3: Confirm the open PR from Task 2 can still be merged**

```bash
gh pr view --repo HuyPhat/reading-list <PR_NUMBER> --json mergeable,mergeStateStatus
```

Expected: `"mergeable": "MERGEABLE"` (it should be, since its `ci` check already passed in Task 2, before protection was even enabled). If it shows blocked for any reason other than the check itself, investigate before considering this task done — don't leave the repo's own CI PR unmergeable.

- [ ] **Step 4: Report final state**

Summarize: the workflow file's path, the PR URL, confirmation it ran green, and confirmation branch protection is active and requires `ci`. Do not merge the PR as part of this task — merging is the human partner's call, same as every other change in this repo.
